# Open questions & risks

Things we don't know yet. Move an item to [[decisions]] (or delete it) once resolved.

- **Can a 60 kg humanoid learn to get up?** Prior now strong YES: the ~70 kg H1-2 did it (arXiv:2603.08619, sim 93.4%, hardware 10/10) with WORSE specific leg torque than the A3 (knee 2.9 vs our 3.1 Nm/kg·m). Waist-pitch worry RESOLVED: the proven route is a HIP sit-up (HoST's G1 has no waist pitch at all; our hip range beats theirs). Remaining unknown is only motion QUALITY at 60 kg (HoST's H1-2 community port "stood but behaved strangely"). Knee range 145° vs G1's 165° is our one kinematic deficit — watch for hip compensation in eval videos.
- **PD gains, armature, and default pose are assumptions**, not AgiBot specs (marked in the manifest). Must be replaced with real actuator specs (AgiBot docs or A3 SDK) before any sim-to-real claim. Single edit point: `configs/robots/a3_ultra.yaml`.
- **Get-up reward weights are first-guess, untuned.** The extension's staged weights (upright 1 / height 2 / target-pose 2.5 / stand-still 1.5) and assist-curriculum thresholds (0.3/0.7, ±0.05 per 4096 resets) are HoST-inspired but never trained to convergence. Expect iteration on the first Lambda runs; watch `getup_success_rate` vs `getup_assist_scale` coupling (assist must reach 0 or the policy is a lie).
- **Assist-force IsaacSim branch source-verified but never executed.** Pre-cloud review confirmed against IsaacLab 2.3.0 source: call signature valid, wrench flushed by `scene.write_data_to_sim()` in the same substep, persistence semantics correct, body_ids/quat conventions correct. Two runtime caveats for the first cloud run: (a) `set_external_force_and_torque` is deprecated in 2.3 → expect DeprecationWarning spam (harmless; holosoma's own gantry/push hit the same path); (b) sanity-check assist actually changes behavior (a few iterations with `EVEREST_GETUP_DISABLE_ASSIST=1` as control). Also watch the first ~50 iterations for base_velocity termination spikes — bank poses were settled in MuJoCo, PhysX geometry differs (mitigated by +1 cm spawn clearance).
- **Holosoma MuJoCo-backend dof-order bug (found in get-up review, affects locomotion smoke too).** The MuJoCo/MJWarp wrapper orders dof arrays in MJCF TREE order (A3: waist-first) but fills `dof_vel_limits`/`torque_limits`/`dof_pos_limits` POSITIONALLY from the config lists (canonical legs-first) → scrambled per-joint limits on that backend only (G1 unaffected: its tree order == config order; IsaacSim unaffected: resolves by name with preserve_order). Local consequences: action-term torque clipping and `limits_dof_pos` reward use scrambled limits in ALL local MJWarp smoke runs (incl. locomotion E06 variant). The get-up extension now builds its own name-mapped limit tensors and is immune on every backend. Consider reporting upstream to amazon-far/holosoma. Cloud IsaacSim runs are unaffected.
- **Early reward is penalty-dominated until first rises.** At the penalty floor (scale 0.1) an untrained policy pays ~0.074/step action-rate against ~0.01–0.05/step task reward; the assist force creating height reward is what breaks the "lie still" optimum. Watch `rew_penalty_action_rate` vs task terms in the first 500 iterations; if the policy goes limp, drop PenaltyCurriculum `initial_scale`/`min_scale` to 0.05.
- **Uncommanded yaw drift (new, 2026-08-14).** The trained policy yaws 3–6°/s with a zero yaw-rate command, and `rew_tracking_ang_vel` finished at 0.559 against the 0.8 threshold in its own config's `nightly.metrics`. The recipe has no heading term in the observation, so heading error integrates by construction. Open: add a heading observation term, or raise the `tracking_ang_vel` weight, on the next locomotion run — decide before spending on M4. Evidence: `docs/sim2sim_locomotion_report.md`.
- **v2 ladder run once; S0/S1 passed, S2–S4 must be re-run (2026-08-16).** See [[experiments]] E09. S0 and S1 both clear **68/68** on the stability grid and are real candidates; S2–S4 were invalidated by the action-rate masking bug and the cold-start iteration budget (both fixed, [[decisions]]). The re-run is S1 (retrain at the unified 692-dim contract) → S2 → S3 → S4, chained by checkpoint, ~15 GPU-h. Still open: (a) whether S1 alone is enough to ship — it already fixes the two defects visible in the E08 videos, and everything after it is arm/terrain capability rather than walking quality; (b) whether to take 100 Hz control (`--simulator.config.sim.control-decimation 2`), which roughly doubles wall clock and changes the ONNX control period (the layout metadata carries it, so the harness follows automatically).
- **`rew_tracking_ang_vel` still misses its own 0.8 gate (2026-08-16).** S1 finished at **0.538** against v1's 0.559 — the heading command did not move the number it was expected to move. The gate is on the *reward*, but the defect it was written for is uncommanded yaw **drift**, which that scalar does not measure directly; the sim2sim angular error did improve (0.406 → 0.150 over training). Decide before the re-run whether the 0.8 threshold is the right gate at all, or whether the drift measurement in `scripts/eval/sim2sim_suite.py` should replace it.
- ~~**The CAM reward's magnitude is an assumption**~~ — **resolved 2026-08-16 by measurement.** The first S2/S3/S4 runs logged `Env/cam_z` at **0.0120–0.0136** m²/s against the assumed `CAM_REF_AMPLITUDE = 0.01`. The limb-momentum estimate was right to within 25%, so the constant stays as it is. (The `Env/cam_xy` companion reads 0.032–0.036, i.e. horizontal CAM runs ~3× the vertical, as expected for a walker.) Both CAM terms use the same constant; nothing further to tune.
- **Arm-amplitude curriculum ran away, not stalled (2026-08-16).** The predicted failure was the opposite of what happened. With `level_up_threshold = 750` against a 1001-step cap, the first S2 run widened to the 100% maximum within 20k iterations and stayed pinned there while the policy was *losing ground* — 800-step episodes cleared the gate on every reset even though a fifth of all episodes were ending in a fall. **A gate that a failing policy passes is not a gate.** Thresholds are now 950 up / 800 down, near the cap. Still open: whether episode length is the right signal at all, or whether the curriculum should key off `rew_tracking_lin_vel` (`docs/final_rl_policy.md` §8) — re-check `Env/arm_amplitude` against `Env/net_reward_per_step` on the next S2.
- **Upper-body skills need an interface decision (new, 2026-08-14).** The locomotion policy owns all 29 DOF and its `pose` reward pins the arms (weight 50), so a manipulation skill *overrides* 14 of its outputs. Measured: 17/28 survive with the arms driven; **28/28 once the arm `dof_pos`/`dof_vel` observation channels are masked** — the failure is off-distribution observation, not balance ([[experiments]] E08b). Open: (a) is masking the permanent contract, or do we retrain with randomized upper-body poses so the policy can actually *use* arm state? (b) masking was only tested on quasi-static poses and ≤1.5 Hz swings — high-momentum motion and hand payloads are untested and could still break it. Decide before any manipulation work is built on top.
- **Which single ingredient breaks the alpine combo?** Rough d1.0, 15° climb, 15° descent, µ0.2 and 2 m/s shoves are each survivable alone; combining them is not (falls at 2.3–8.3 s). Worth an ablation before the Everest fine-tune, so M4 targets the actual coupling rather than adding difficulty blindly.
- **Does the v5 asset change locomotion behavior?** v5 adds 16 collision boxes over the E01 asset and makes hip links contact-capable — "hip" termination fires slightly earlier on falls. Watch nefc counters on the first v5 locomotion run.
- **Terrain handoff not delivered.** Tomasz's Everest terrain generator plugs into `TerrainSpec`/`TerrainPatch`; E10/E15 (the whole Everest fine-tune phase) blocked until it lands. Interim option: GeologicDome's existing reconstructions.
- ~~**ONNX action scaling**~~ — resolved 2026-08-14. The export embeds both the observation normalizer and the per-joint action bounds, so the consumer applies only the uniform `action_scale` 0.25 around the default pose. `docs/onnx_policy_interface.md` was also wrong about the observation order (it is alphabetical by term name) and the phase width (2, not 1); the verified contract now lives in `everest_locomotion/evaluation/sim2sim.py`.
- **W&B credentials not configured** — TensorBoard only for now.
- **FastSAC vs PPO on A3** (E07) — undecided until both are reasonably tuned.
